# Correction — Reproducibility Defects in the v1.0 Shipping Package

**Issued 2026-08-22. Package version v1.0.2.**
**Nothing in `docs/WRITEUP_v1.0_EN.md` is amended by this document. No number changes.**
**中文版見文件下半（§ 中文摘要）。**

---

## What this is

An external reviewer cloned this repository, ran the commands listed under
README's *"Verify the numbers yourself"*, and found that some of them did not
work. We reproduced every one of their findings on our own machine, found three
more they had not reached, and fixed all of them. This document records what was
broken, what it would have shown a reader, and what we changed.

The headline claim of this repository is that every number can be recomputed
from shipped raw outputs. **For the v1.0 causal results, that claim was false as
shipped.** It is true as of v1.0.2. The correction is disclosed here rather than
quietly patched, and the defective package remains retrievable in the version
history.

---

## 1. The serious one: a silent false falsification

`harness/causal_analysis.py` reads its smoke-gate values from a file. The lookup
at lines 464–466 tries three candidate filenames in order:

```
results/causal/smoke_eval_{run_id}.json          # not shipped
results/causal/smoke_eval_winA2-20260822.json    # correct file — NOT SHIPPED in v1.0
results/causal/smoke_eval_winA20260822.json      # a different run — the only one shipped
```

The two filenames differ by a single hyphen. Because the third candidate existed
in the package, the lookup succeeded, **no error was raised**, and the analyzer
quoted values from an unrelated earlier smoke run.

The consequence, measured by us on the v1.0 package:

| field | correct file (`winA2-20260822`) | file actually shipped (`winA20260822`) |
|---|---|---|
| `g1.verdict` | `proceed：存在 Δs 以外結構` (proceed) | `G1-a：全部有效格 pooled ≈ 底線（一致決）→ 設計死，主實驗不跑` (**design dead, do not run the main experiment**) |
| `noise_floor.floor_nats` | `1.4341e-4` | `0.22938` (**1600× larger**) |
| example `ratio_over_floor` | `528.75` | `0.35` |
| `positive_control` (as quoted downstream) | pass recorded | `None` |

A patient third party, having repaired the two loud failures described in §2,
would then have been handed a report — generated by our own shipped code —
stating that this design is dead and the main experiment should never have been
run. **Silently.** That is worse than a crash: a reader who hits a crash asks the
author; a reader handed a plausible false verdict does not.

**Fix:** `smoke_eval_winA2-20260822.json` is now shipped, so the lookup resolves
on the correct candidate and the fallback never fires.

**Deliberately not fixed:** the fallback chain itself. `causal_analysis.py` is a
frozen analyzer whose hash was recorded at ignition; editing its logic after
unblinding would break the freeze chain that is this project's main methodological
claim. The hazard is therefore disclosed here instead of silently engineered away.
A reader who wishes to check this can delete the correct file and observe the
substitution for themselves.

## 2. Missing execution dependencies

Four kinds of file that `causal_analysis.py` reads or imports were absent from
the v1.0 package. In dependency order, each was hit only after the previous one
was repaired:

1. **`planning/office_reports/theory_v3_sim.py`** — imported and executed at
   `causal_analysis.py:44` (`FROZEN_SIM`). Absent ⇒ `FileNotFoundError` at the
   first line of `analyse()`. Loud.
   This omission was in fact already recorded in our own build report
   (`planning/office_reports/build_v1.0_bundle_report.md:96–98`) as an
   "unfulfilled promise" — but filed under *documentation inconsistency*. Nobody
   noticed that the missing item was not a cited document but an executed
   dependency of the headline analyzer.
2. **The five per-model patch record files** (`main_winB1_patch_*.json`, 5.2 MB).
   The package shipped `main_winB1_patch_runs.json`, which is the merged artifact
   produced by `causal_main.py --stage genmerge` for `causal_smoke` — not the
   per-model records (`.model` / `.records`) the analyzer requires. Absent ⇒
   `no usable patch files`. Loud.
3. **`smoke_provenance_main_winB1.json`** — the provenance trace. Absent ⇒ 21
   gate-rejected pairings (299 keys) silently missing; the trace degrades from
   "family statistic uncomputable" to "one family's data absent". Quiet.
4. **`smoke_eval_winA2-20260822.json`** — §1 above. Silent and actively harmful.

Two further analysis scripts had missing inputs of the same kind, found by the
clean-room test in §5 rather than by inspection:

- `battery/verbcue_items.json` and `battery/verbcue_cell_config.json`
  (`verbcue_aggregate.py`, `verbcue_main.py`)
- `planning/office_reports/theory_pos_test_mapping_v1.md` (`pos_test_v221.py`)

**Fix:** twelve files added to the package whitelist in `harness/build_bundle.py`,
with the reason for each recorded inline. Package: 138 → 151 files, 25.1 → 30.6 MB.

**Verification of the repair:** with all four dependencies restored, the recomputed
output was compared leaf-by-leaf against the already-shipped
`results/causal/analysis_main_winB1.json`: **1320 values, 0 differences.** The
published numbers were correct; only the means of recomputing them were missing.

## 3. Integrity manifest broke on checkout

The reviewer measured 92 of 138 `MANIFEST.json` hashes failing on a fresh clone.
On our machine all 138 matched. Both are true: 95 of the shipped files carried
CRLF line endings (they were generated on Windows), and git normalises line
endings on checkout when `core.autocrlf` is set. The file contents never changed;
the fingerprints travelled badly.

For a package whose stated guarantee is auditable integrity, this defect is
especially costly: it converts every independent verification attempt into a
false alarm.

**Fix:** a `.gitattributes` containing `* -text` is now generated into the package
root and recorded in the manifest.

**Verification of the repair (measured, reproducible):** the package was
initialised as a git repository with `core.autocrlf=input` — the setting that
produces the reviewer's failure — committed, and cloned. Verifying the manifest
against the *cloned* files gives **151 / 151 matching, 0 mismatches.**

```bash
git init . && git config core.autocrlf input
git add -A && git commit -m "test" && cd .. && git clone ./pkg ./clone
cd clone && python - <<'PY'
import json, hashlib, os
m = json.load(open("MANIFEST.json", encoding="utf-8"))
bad = [e["path"] for e in m["files"]
       if not os.path.exists(e["path"])
       or hashlib.sha256(open(e["path"], "rb").read()).hexdigest() != e["sha256"]]
print(f"{len(m['files']) - len(bad)} / {len(m['files'])} match; mismatched: {bad}")
PY
```

**Unresolved:** the reviewer additionally reported that 4 of the 92 were *genuine
content* differences rather than line-ending artifacts. We could not reproduce
this — under `core.autocrlf=input` all 92 were line-ending artifacts and 0 were
content differences. We are not entitled to conclude either that they were
mistaken or that the four were also CRLF. **If you are that reviewer: please send
the four filenames and their diffs.**

## 4. Hard-coded local paths

Three shipped scripts contained absolute paths from the machine they were written
on:

| file | line | was |
|---|---|---|
| `results/l0p/audit_l0p_independent.py` | 124 | `C:\Users\...\Temp\claude\...\<uuid>\scratchpad\audit_results.pkl` |
| `results/l0p/audit_l0p_permutation.py` | 14 | same path (read side) |
| `results/relative_depth/independent_check.py` | 42–43 | `D:/ai/research/omtr/results/...` |

The first two ran successfully on our machine only because that one-off temporary
directory happened not to have been cleaned up yet; they would fail on any other
machine, any other account name, or after Windows clears its temp folder. The
third points at a directory that no longer exists on any machine, including ours.

**Fix:** the first two now use `tempfile.gettempdir()`; the third derives the
repository root from `__file__`. No computation was altered — only where an
intermediate cache is written and where inputs are located.

**Scope note on disclosure:** `results/l0p/audit_l0p_independent.py` was released
as an execution-identical second implementation. This edit changes the location of
a side-effect file only; no computed value is affected. It is disclosed here rather
than made silently.

**Not a privacy breach:** a full-package scan for the author's real name, age, and
other handles returns zero hits. What leaked was the Windows account name `USER`
and a session UUID — a hygiene and portability defect, not an anonymity one.

## 5. The process defect underneath all of this

Every one of the above passes on the authoring machine and fails elsewhere. That
is not a coincidence; it is the shape of the gap.

The pre-upload checklist **already required** most of these checks.
`PRE_UPLOAD_CHECKLIST.md:27` explicitly names `C:\Users\...` machine paths as a
thing to scan for, and the scan was performed — it caught such paths in `.md`
files and missed them in `.py` files, because whoever ran it was thinking about
*documents a reader reads*, not *code a reader runs*. `RELEASE CHECK ④` verified
that "all paths named in README exist"; all 19 did. Nobody typed the commands.
The dependency that broke is named inside the code, not in the README.

So the failures did not land inside any check. They landed **between** checks —
in the seams between the department that owns documents and the department that
owns code, between "the file exists" and "the command runs", between "we read
that paper" and "the bibliography is built from a different file". Adding a ninth
check would add a ninth seam.

The single measure that would have caught all of them at once is cheap and was
never performed even once:

> **Unpack the package into a folder unrelated to the project, and run every
> command the README lists. All must pass before upload.**

This is now implemented as `harness/verify_shipping.py` and is a release gate.
It is the only new rule introduced by this correction.

## 6. Related work that should have been cited

Independently of the reviewer's engineering findings, they identified a
literature gap. We obtained and read the full texts. Our conclusions:

- **Zhang, Ippolito, Lee, Jagielski, Tramèr & Carlini,
  *Counterfactual Memorization in Neural Language Models* (arXiv:2112.12938).**
  This is the canonical prior treatment of the problem §3 of the write-up
  describes, and its motivating sentence is close to ours — verbatim from the
  full text: *"One issue with these extraction attacks is that they often
  identify primarily 'common' and frequently occurring strings in the training
  set."* **It should have been cited and was not.** It is not preempting: its
  operationalisation is *near-duplicate count in the training set* (the string
  "predictable" does not occur anywhere in it), whereas we ask whether a distinct
  internal circuit exists; and its estimator is expensive by construction —
  verbatim: *"we train 400 models for each dataset, each on a random 25% subset
  of the training examples"* — which is not runnable on the hardware used here.
- **Tiwari, Trachtenberg & Suh, *Prior Aware Memorization* (arXiv:2602.18733).**
  Confirmed to exist; title and authors as reported. It makes the same diagnosis —
  that likelihood-threshold definitions "may misclassify popular sequences as
  memorized" — but its method is a probability-ratio score computed from forward
  passes; a full-text search for activation patching or ablation returns nothing.
  Corroborating work, not a preemption.
- **Hubble (arXiv:2510.19811)** names the same confound and provides a controlled-
  insertion model suite. It is the most natural future platform for this question
  and is recorded as such.
- **arXiv:2412.18497 (*Think or Remember?*)** — we had read this in full before
  publication and recorded a written threat assessment concluding it studies a
  different construct (replication of seen *incorrect* answers on synthetic tasks,
  with no predictability-matched control; "predictab*" occurs zero times in it).
  **That decision stands, but it lived in an internal file and never reached the
  reader.** A decision not to cite, taken on evidence, is invisible unless it is
  written down where the citation would have been.

**How these were verified, including one failure of ours.** The three full texts
were downloaded to local files and quoted by grepping the raw source, not by
asking a tool to summarise them. This mattered: an earlier draft of this section
carried the first quote as *"primarily identify 'common' and frequently
occurring strings"* and stated the cost as "on the order of 10³ models". Both came
from an assistant's report, both were wrong — the paper says *"often identify
primarily"* and *"400 models for each dataset"*. Neither error changed the
conclusion, and both would have shipped as verbatim quotations had the raw files
not been checked. This is the seventh transcription-layer error this project has
caught, and the reason its standing rule is that any quotation entering a verdict
must be grepped from a local copy of the source.

**Open, and not answerable by us yet:** Hubble cites a 2024 paper by Huang et al.
as the origin of the "difficulty disentangling *easy* from *repeatedly trained on*"
framing. We have not read it. Under this project's own rule, knowing that a paper
exists licenses no statement about it in either direction. It is the outstanding
item on this thread, and checking it costs nothing but time.

## 7. One reviewer finding we examined and rejected

The reviewer argued that the equivalence bounds (0.309 nats Pythia, 0.514 nats
OLMo) are weak because they are one-quarter to one-half of the −1.10 to −1.13
nats effect observed on the secondary arm, and that the abstract therefore
overclaims.

**We disagree, and the direction matters.** An equivalence bound *narrower* than a
comparison effect means the instrument resolves that magnitude and did not find
it — that is the premise of the claim, not a hole in it. A bound *wider* than
−1.10 would be the vacuous case. `harness/causal_analysis.py:213–215` states this
direction explicitly and records that an earlier comment had it backwards.
Adopting the reviewer's reading would restate a strong result as a weak one.

We also note that the bounds and both realized sample sizes already appear in the
abstract-level text (`README.md:21–23`), which the reviewer's framing did not
reflect.

**But two things they were reaching for are genuinely absent from that level, and
we accept those:** the design's own resolution floor, and the flag that OLMo's
n = 6 falls below the frozen table's smallest key (8), so that boundary is
extrapolated — stated only in a table row at `docs/WRITEUP_v1.0_EN.md:324`.
Both belong in the abstract-level summary of any future revision.

**Also accepted:** §3's entanglement observation carries no section-level
"not preregistered" stamp, though §7 carries one. It should. Its first measurement
(`gate_decay_probe.py`, 2026-08-21 22:24) postdates both preregistrations
(21:42 and 15:02), so it is exploratory. This is also why we decline the
reviewer's suggestion to promote it to the headline: doing so would present an
exploratory finding as a confirmatory one, which is precisely the failure mode
this project's preregistration discipline exists to prevent.

# 中文摘要

一位外部審閱者把這個倉庫 clone 下來，照 README 的「Verify the numbers yourself」
把指令敲了一遍，發現有幾道跑不動。我們在自己機器上把他講的每一條都重現了，
另外找到三條他還沒走到的，全部修好。這份文件記錄壞了什麼、它會讓讀者看到什麼、
以及我們改了什麼。

**這個倉庫最大的賣點是「每個數字都能從隨包出貨的原始輸出重算」。就 v1.0 的因果
結果而言，出貨當時這句話是假的。** 到 v1.0.2 才成立。我們選擇公開更正而不是
默默修掉，有缺陷的那一版留在版本歷史裡。

**最嚴重的一條（§1）**：分析器找不到正確的檔案時不會報錯，會去抓一個名字只差
一個連字號的別次紀錄，然後印出「設計死，主實驗不跑」、雜訊底線差 1600 倍。
一個有耐心的陌生人，修好前面兩個「大聲壞掉」的地方之後，會用我們自己出貨的
程式，安靜地拿到一份否證我們已發表結論的假報告。**炸掉的人會來問作者；
拿到假結果的人不會。**

**底下的流程病（§5）**：這些缺陷全部是「在作者機器上好好的、換個人就壞」。
而檢查清單上其實**都有寫**——`PRE_UPLOAD_CHECKLIST.md:27` 白紙黑字要掃
`C:\Users\...` 這種機器路徑，也真的掃了，但掃的人心裡想的是「哪些**文件**會被
讀」，所以抓到 `.md`、漏掉 `.py`；`RELEASE CHECK ④` 查「README 提到的路徑存不
存在」，19 條全在——但沒有人真的把那些指令敲下去。壞掉的相依寫在程式裡，不在
README 裡。

也就是說，漏網的東西沒有掉在任何一項檢查**裡面**，全部掉在檢查與檢查**之間的
縫**。再加第九項檢查只會多出第九道縫。

能一次抓到全部、而且從來沒做過一次的，是這件事：

> **把出貨包解到一個跟專案無關的資料夾，README 上寫的每一道指令實際跑一次。
> 全過才准上傳。**

已實作為 `harness/verify_shipping.py`，列為發布關卡。這是本次更正唯一新增的規矩。

**數字沒有變**：四樣相依補回去後重算，跟已出貨的 `analysis_main_winB1.json`
逐葉比對 1320 個值 0 差異。已發表的數字是對的，缺的是讓別人算得出來的東西。
