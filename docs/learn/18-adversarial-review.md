# 18. 對抗式審查（Adversarial Review）

**一句話白話版**：對抗式審查是「先找一群預設不相信你的人來挑你程式的錯，而且每個挑出來的錯都要真的重現一次才算數」——分成兩個角色：**主張方**負責挑毛病、指出「這裡看起來有問題」；**查核方**的立場預設是不相信，要求實際跑一次程式重現問題，才把這個發現升級成「確認」。不是走個形式的「大家看一看」。

**為什麼本研究用得到**：我們的量測程式（harness）要在真正的 GPU 上連續跑上百題，任何一個隱藏的 bug 都可能讓一整夜的實驗數據全部作廢——輕則指標算錯方向、重則模型根本沒載入成功、整批直接報錯。與其事後才發現，不如把審查的時間成本花在燒卡之前，把地雷先排掉——這在製作過程的第九步真的攔下了一顆會讓整個 pilot 直接爆炸的地雷。

**再深一點**：這個制度的關鍵在於「查核方預設不信」——如果只讓一個角色「看起來覺得有問題」就算數，審查報告會充滿模糊的懷疑，把修復力氣浪費在不存在的問題上；要求查核方自己動手重現，才能把誤報壓低。我們這次跑了 21 個代理、263 次工具呼叫，篩出 **16 個「查核方實跑重現過」的確認缺陷**，另外 2 個主張方提出但查核方跑不出來的，就標記成誤報、不修。誤報率 2/18 大約一成——代表主張方的直覺大部分時候是對的，但那一成的差距正是查核方存在的價值。

**在我們的程式碼／數據裡**：這次審查修復的成果直接寫進 `harness/run_pilot.py` 檔頭的 docstring 第 1 行——「OMTR pilot runner v2（依對抗式審查 16 項確認發現重寫）」。裡面最致命的一個缺陷是工具鏈相容性炸彈：`load_model()` 函式（第 39–50 行）的相容性 shim，處理的問題是 TransformerLens 3.7.3 的 NeoX 模型轉換器程式碼仍在讀取一個叫 `embed_out` 的零件名稱，但新版 transformers 函式庫早已把它改名成 `lm_head`，兩邊對不上就會在載入 Pythia 的第一秒直接報錯。查核方不只確認了這個 bug 會重現，還實測出修法——第 46 行 `hf_model.embed_out = hf_model.lm_head  # TL 3.7.3 converter 相容 shim`：自己先組好 HuggingFace 模型、手動把新名字掛回舊名字當一個別名，再把這個「偽裝過」的模型交給 TransformerLens 讀。這行如果沒被審查揪出來，會在真正跑 pilot（要連續跑上百題、耗掉一整晚 GPU 時間）的第一步就整批爆炸——正是「TL 相容性炸彈在燒卡前被攔下」的具體案例。

**常見誤解**：
1. 「審查找到的問題越多，代表程式寫得越爛」——反過來想才對：找到問題但在燒卡前修好，是審查制度發揮作用的證據；真正糟糕的是審查沒找到、燒了一整晚 GPU 才發現全部作廢。
2. 「有審查團隊看過就一定沒問題了」——不對，我們自己的紀錄就有 2 個誤報——查核方存在的意義正是防止「主張方看走眼」被直接寫進最終報告；審查制度是降低風險，不是把風險歸零。

**答辯模擬題**：
- Q：花時間讓一堆 AI 代理互相審查，不會比直接動手跑實驗更浪費資源嗎？
  A：這次審查抓到的相容性 bug，如果沒抓到，會在真正的 pilot（連跑上百題、耗掉一整晚 GPU）的第一步就讓整批數據作廢——審查花掉的時間，遠低於重跑一次失敗實驗要付出的成本，這正是「先審查、後燒卡」這個紀律划算的地方。
- Q：「16 個確認缺陷、2 個誤報」這個數字你怎麼知道誤報真的是誤報，不是查核方自己也看走眼？
  A：誤報的判定標準是「查核方實際執行程式、重現不出主張方講的問題」——這本身是可重複驗證的動作，不是憑感覺喊誤報；當然這不保證絕對零漏網，但比起沒有查核方這一關、只靠主張方單方面判斷，錯誤率已經大幅壓低。
