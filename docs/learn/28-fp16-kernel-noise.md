# 28. fp16 kernel 噪音（Floating-Point Kernel Noise）

**一句話白話版**：同一台計算機、同一個問題，只因為內部換了個「先加哪個數、再加哪個數」的運算順序（浮點數計算路徑），答案就飄了 0.2——不是題目變了，是尺子本身在抖動。**如果你要量的東西比尺子的抖動還小，那把尺這時候就不是尺了**，量出來的數字沒有意義。

**為什麼本研究用得到**：這正是判斷「兩個條件是不是共用同一條恢復曲線」（見卡 26 講的 G1 判定）的門檻依據——如果量到的殘差（實測跟理論預測的差距）比儀器本身的噪音還小，那不是「沒有結構」，是「這把尺量不出結構」。本研究一開始用 fp16（半精度浮點數，用比較少的位元存一個數字，省記憶體但比較不準）跑，踩到這個坑：同一個介入只是換了一下批次組成方式，答案就能飄到 0.033～0.229 nats（自然對數機率的單位），遠超過需要偵測的訊號規模。

**再深一點**：三條獨立證據判定「這是 fp16 數值累積誤差，不是別的 bug」：
1. **構造上不可能是別的原因**：批次組成方式是同一列資料複製 N 份，長度內容完全相同，沒有補零、沒有位移，遮罩或位置編碼的 bug 沒有機會發生。
2. **換精度就換量級**：同一條運算路徑，fp32（單精度）的飄動只有 7.4e-6～1.4e-4，fp16 卻是 0.033～0.229——差 675 到 4919 倍。遮罩或位置的 bug 不會挑精度，兩種精度應該一起壞或一起好。
3. **形狀是階梯狀且會封頂**：某一題在 fp16 下，批次從 1 個變 2 個變 4 個，答案分別往上跳（1.6682→1.7315→1.8975），但批次從 4 變 8 時，答案逐位元完全一樣。這正是矩陣運算函式庫（cuBLAS）在超過某個批次大小之後，換去用另一種運算切塊方式的簽名——真正持續累積的誤差不會突然停在同一個數字上。

三條證據方向一致，才敢下這個判定，不是憑感覺說「大概是精度問題」。修法是把整個模型的算術都升到 fp32，但這裡有個容易誤讀的地方：**升精度不是「找回更準的模型」**——存檔的模型權重本身就是用 fp16 存的，fp32 只是讓「算加法、算乘法」這個過程比較準，不是把不存在的資訊找回來。而且只把最後一步（算分數那一步）升 fp32，效果很小（只改善 2%），因為誤差是散布在 24 層裡累積的，不是集中在最後一步，所以沒有便宜的局部修法，只能整個模型都用 fp32 跑。

**在我們的程式碼／數據裡**：`results/causal/diag_fp16_batch.json`（批次組成 × 精度的完整掃描數據）；`planning/rig_build_report.md` §5.8.1（三條證據與根因判定的完整推導）；`gold_readout_from_logits` 已經把算分數那步強制用 fp32（`log_softmax(logits.float(), -1)`）；`diag_fp32lens.json`（只升最後一層的實驗，量到 2% 改善，證明局部修法無效）；§5.8.4 換成 fp32 後底線縮小到 1.434e-4，殘差比底線高出 53 到 1409 倍，G1 才第一次真的量得出東西。

**常見誤解**：
1. 「把運算精度升到 fp32 就是找回更準的模型」——不對，checkpoint（存檔的權重）原生存的就是 fp16，fp32 上轉只是讓「算術過程」比較準，不是「模型記得更清楚」。這句話要講清楚，否則會被讀成我們找回了不存在的精度。
2. 「只要最後算分數那一步用 fp32 就夠了」——不對，實測只改善 2%，誤差散布在 24 層，只有整個模型都用 fp32 才有用。

**答辯模擬題**：
- Q：為什麼不乾脆全部用 fp16 跑，省時間省記憶體？
  A：因為我們量到 fp16 的批次組成誤差（0.033～0.229 nats）跟我們要偵測的效應是同一個量級——尺子的抖動蓋過了訊號，量出來的東西沒有意義。改用 fp32 之後，底線縮小到 1.4e-4，殘差比底線高出 53 到 1409 倍，才第一次真的量得出來。
- Q：你們怎麼確定那個飄動是浮點數的問題，不是程式寫錯？
  A：我們有三條獨立證據：批次的組成方式構造上不可能碰到遮罩或位置編碼；fp32 同一條路徑的飄動小了三個數量級以上；飄動的形狀是階梯狀會封頂，符合矩陣運算庫換運算方式的特徵，不是誤差線性累積的長相。三條證據方向一致，才敢下這個判定。
