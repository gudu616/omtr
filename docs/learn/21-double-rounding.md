# 21. 數字對帳與雙重捨入（Number Reconciliation & Double Rounding）

**一句話白話版**：「雙重捨入」是先把數字四捨五入到三位小數、再從三位版本捨到兩位——結果可能跟「直接從原始值捨到兩位」不一樣。例如原始值 0.0745356：直接取兩位是 **0.07**，但先取三位變 <!--quoted-error-->0.075、再取兩位就變成 **<!--quoted-error-->0.08**——兩條路走出兩個答案，而只有第一條是對的。

**為什麼本研究用得到**：論文審查裁決書把「所有數字都能從原始資料重算」列為必須用機器看守的承諾（P0 級）。我們寫了一支對帳程式 `harness/reconcile.py`，把稿件裡每一個數字拿去跟原始 JSON 重算比對。掃描 v0.3 凍結稿的結果：**對帳到 307 個數字、抓出 8 個真缺陷**（299 對、8 錯；修正後重掃 308 個全綠，閘門再升級後覆蓋擴到 332 個、依然零錯），其中六處正是雙重捨入——因為稿件是人（和 AI）從中間報表抄數字，中間報表已經先捨過一次位了。

**再深一點**：對帳程式不能太笨也不能太兇。太笨——只搜字串會「掃到 0 個數字然後宣布全部通過」（真空綠燈，我們的第一版就犯了這個錯）；太兇——把「−0.846 寫成 −0.85」這種合法捨入也判死刑，會淹沒真問題。最終版用「值基準比對」：從原始值出發，算出所有合法的捨入變體，稿件數字落在變體集合內就放行，落在外面（例如雙重捨入的產物）就報警。程式自帶六個自檢案例（`--selftest`），先證明自己會抓、也會放，才有資格去審稿件。

**在我們的程式碼／數據裡**：八個缺陷的完整清單見製作歷程（`PROCESS_LOG.md`）第十八步。最典型的兩個：OLMo 的語料次數~深度相關，原始值 −0.734632，稿件寫成 <!--quoted-error-->−0.74（先捨到 <!--quoted-error-->−0.735 再捨上去），正確是 −0.73；劑量反應表的 <!--quoted-error-->+0.08 同理應為 +0.07。另有一處不是捨入而是「慣例不一致」：標準差有兩種除法慣例（除以 n 或 n−1，程式參數叫 `ddof`），稿件的 <!--quoted-error-->1.32 修成 1.36 並標注慣例。

**常見誤解**：
1. 「差 0.01 而已，有差嗎？」——單看一個數字沒差，但審查者的邏輯是：連能機械驗證的數字都對不上，讀者憑什麼相信那些不能機械驗證的主張？數字錯的殺傷力不在數值，在信用。
2. 「用 AI 抄數字比人抄可靠」——這 8 個錯大多正是 AI 從中間報表抄來的。可靠的不是「誰來抄」，是「有沒有一台機器在對帳」。

**答辯模擬題**：
- Q：你們的數字是 AI 寫的，怎麼保證沒抄錯？
  A：不靠保證，靠對帳程式——稿件裡 308 個數字每一個都重算比對過，程式和原始資料都隨 repo 公開，任何人可以自己重跑一次 `reconcile.py` 驗證。
- Q：對帳程式自己有 bug 怎麼辦？
  A：它有六個自檢案例（該抓的抓到、該放的放行），而且它的判定是保守的——報警的 8 個我們逐一回到原始 JSON 手動確認過都是真缺陷，不是程式說了算。
