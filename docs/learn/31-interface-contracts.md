# 31. 介面契約與「等它炸是最貴的做法」（Interface Contracts）

**一句話白話版**：兩個人各自負責蓋房子的兩段樓梯，如果沒先講好每一階的高度，蓋到中間對接的時候很可能一邊高一邊低——兩邊都沒做錯自己那一段，但接不起來。程式裡也一樣：兩支程式如果對「同一份資料長什麼樣子」有不同的想像（這叫**介面契約**），接資料的時候不會有人提醒你，程式就會在半夜炸掉，或更可怕的——**不炸，但默默算出錯的答案**。等它炸出來才發現，是最貴的抓法。

**為什麼本研究用得到**：因果階段的驅動程式分成兩支：`causal_smoke.py`（窗口 A 冒煙用，已凍結）跟 `causal_main.py`（窗口 B 主實驗用，後寫的）。兩支程式都要讀寫同一批 JSON 資料，但各自對「資料長什麼形狀」的假設不一樣——這在窗口 B 當晚（主實驗真的在跑的那一夜）一口氣炸出五個同一種病因的錯誤，逼著整晚都在修接口，而不是分析數字。

**再深一點**：舉三個具體的例子。

第一個，**「runs 鍵」問題**：`causal_smoke.stage_provenance` 這段程式，第一行就是去讀 `data["runs"]`，但 `causal_main` 產出的資料是「逐模型分片」的格式（每個模型一個檔案，裡面是 `{"model":..., "records": {題號: 紀錄}}`）——冒煙那邊記錄存的是清單（list），主跑這邊存的是字典（dict）。兩邊一接上就是 `KeyError: 'runs'`。報告原話：「兩支程式對同一段資料有兩種形狀，誰都沒錯，就是沒對過。」

第二個，**dof=−2（自由度算成負的）**：判斷「這一題內部有沒有結構」需要每題至少兩個資料點才能算，但原本的程式只把「主要選中的那一個腐蝕」放進散點圖，跨替換詞的點完全沒進去——於是每題永遠只有一個點，自由度算出來是負 2，這個判定天生不可能成立。是器材部自己在接線分析腳本時抓到才修的。

第三個，這裡先解釋一下這個詞的由來：patching 要貼回去的是模型某一層附近的一段狀態，程式裡管這叫「band」（層帶），跟訊號處理裡「頻帶／頻寬」是同一個字。後面幾個分析步驟（像 `stage_glink`）靠「模型、題號、層帶」三個欄位去把兩份 JSON 資料兜起來，但沒有任何程式檢查兩次跑用的是不是同一組層帶設定——**如果一次用某個層帶範圍，另一次用別的範圍，兩邊對不上的格子會靜默地變成 `null`，不會報錯，只會少一塊資料，沒人會發現**。報告裡明白寫著：「目前只靠人自己記得，程式沒有比對兩份的 config。」

這五隻蟲（那一夜總共抓到五個）有一個共同形狀，報告自己講得很白：「同一個量有兩條路算，遲早會漂；解法是砍到剩一條，不是兩邊都記得改。」意思是——與其指望兩支程式的作者都記得同步改設定，不如把「哪些題目算是這一類宿主」這種共用邏輯抽成程式裡**唯一一份**常數，兩邊一起讀同一份，想漂都漂不了。

**在我們的程式碼／數據裡**：`planning/rig_build_report.md` §5.11.8（「溯源段介面契約破裂」——runs 鍵形狀不合，修在 `causal_main.py` 新增 `--stage genmerge` 把分片併成 runs 形，刻意不動已凍結的 `causal_smoke.py`）；§5.6（G1 散點 dof=−2 的抓法與修法）；§5.11.5（`GEN_HOST_LEVELS` 抽成單一常數，budget 段與 gen 段共用，解決「同一條規則寫在兩個地方」）；§7 已知限制第 6 條（`--bands` 不一致會靜默對不上，目前無硬檢查，留給評審裁示）。

**常見誤解**：
1. 「介面對不上，炸出來就修一修，沒什麼大不了」——對一半。真正貴的不是修 bug 本身，是「炸在半夜、炸在資料已經跑了一半的時候」，還有「炸不出來、默默給錯答案」那種更危險的情況（比如層帶不一致時只是少一格 `null`，不會有任何錯誤訊息）。
2. 「這種 bug 是粗心，跟研究設計沒關係」——不對，這類 bug 直接影響「能不能相信手上的資料」，本研究把它們當成跟統計裁決同等重要的東西誠實記錄，而不是修完就當沒發生過。

**答辯模擬題**：
- Q：為什麼會有兩支程式對同一份資料有不同形狀的假設，一開始講好不就沒事了？
  A：因為 `causal_smoke.py` 是窗口 A 冒煙用的，凍結在先；`causal_main.py` 是後來為窗口 B 主實驗另外寫的，兩支程式產出資料的方式不同（一個整批存，一個逐模型分片存，方便中途斷點續跑）。這種分歧不是沒溝通，是兩支程式在不同階段、為了不同的需求分別演化出來的，只是誰都沒有回頭去核對格式。
- Q：這些 bug 會不會影響已經凍結的窗口 A 結果？
  A：不會。修法刻意保留 `causal_smoke.py` 完全不動（報告裡寫明「那支產出了窗口 A 的凍結數字，解盲前不碰它是比較便宜的保守」），所有修正都做在 `causal_main.py` 新增的轉換層（`genmerge`）上，而且轉換只轉形狀，不重算不篩選不重排，重跑之前還先驗證過轉換後的資料能被下游程式正確讀取。
