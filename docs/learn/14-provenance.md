# 14. 語料溯源與 infini-gram（Corpus Provenance）

**一句話白話版**：n-gram 是「連續 n 個詞組成的一小段文字」（例如 7 個詞一組叫 7-gram）；infini-gram 是能瞬間回答「這一小段文字在某個訓練語料庫裡出現過幾次」的搜尋引擎，本研究拿它給「模型是不是真的背過這段話」找鐵證。

**為什麼本研究用得到**：本研究選 Pythia-1.4B 和 OLMo-2-1B 的唯一理由就是它們的訓練語料完全公開（Pile、Dolma/olmo-mix）——可以直接查「這句話在它讀過的教材裡出現幾次」，不用像 Claude 那樣訓練資料是黑盒子只能用猜的。這是整個任務階梯（卡12）的 ground truth 儀器：沒有它，L0（背過）、L0N（沒背過）、L5（新穎）全部無從驗證。

**再深一點**：`harness/verify_battery.py` 不是把整段 88 詞的文字丟去查一次，而是用滑動視窗切成一串探針——`probes_from()` 預設 `n_words=7`、`stride=4`（每 7 詞一組、每次滑 4 詞，相鄰窗口重疊），一段話切成好幾個探針分別查兩個語料索引（`v4_piletrain_llama` 給 Pythia、`v4_olmo-mix-1124_llama` 給 OLMo-2）。這樣做的原因：完全比對對長句子太嚴格（一個標點不同就查無），多個窗口還能互相佐證——真的被背過的段落，前中後段應該全部大量查到。

「0/20 事故」與「70% 窗口規則」的由來（`docs/PROCESS_LOG.md` 第十一步）：改良版驗證器上線後，20 段名著（連《傲慢與偏見》《創世記》都在內）驗證全部掛零，一看就是程式錯了不是世界錯了。診斷過程：第一個假設（剝標點的正則式壞了）用單發查詢測試，結果誤導了自己——挑到的例子剛好去掉逗號的版本網路上也常見；換個方法，直接打開驗證結果的原始數據看模式，真相才現形：只有跨句界的窗口全部掛零（「daughters. "My dear Mr. Bennet," said…」被錯剝成「daughters My dear Mr Bennet said」，世上不存在這種寫法），句子內部窗口全部健康（171、148 這種正常計數）。根因是正則式本來只想剝窗口最外緣的引號，卻套用到了每一個詞的頭尾，結果每個句子中間的句號、逗號全被吃掉。修法兩層：`_edge_trim()` 現在只剝窗口首尾兩個詞的邊界標點，內部原樣保留；判定規則從「全部窗口過門檻」改成 `MEMORIZED_FRAC=0.7`（見 `_judge()`）——至少 70% 窗口過門檻就算「確定背過」，因為跨句窗口天生會因引號體例（直引號、彎引號、有無句號）在不同轉載版本間變異，不該有一票否決權。

**在我們的程式碼／數據裡**：`query()`（回傳三態 `status ∈ {ok, invalid, network}`，4xx 錯誤不重試、限流則長退避重試）、`_judge()`（`memorized` 模式用 `L0_COUNT_THRESHOLD=20` 搭配 `MEMORIZED_FRAC=0.7`，`control` 模式反過來要求 `CONTROL_MAX_COUNT=2` 全部窗口都不能超）、`check_novelty()`（給 L5 用，回傳連續量 `frac_present`／`max_count` 而不是單一布林值）。輸出檔案：`battery/l0_verification.json`、`battery/l0n_verification.json`。

**常見誤解**：
1. 「infini-gram 查到 count=0 就代表模型絕對沒見過這個概念」——不對，count=0 只代表這個精確的詞序組合沒有逐字出現過，模型仍可能學過構成這句話的所有詞彙和相關知識（見卡13）。
2. 「一個探針查不到就代表整段話沒背過」——正是 0/20 事故的反面教訓：單一探針可能因切分位置、標點差異而失真，要看大多數窗口的一致模式，不能被單一異常值牽著走。

**答辯模擬題**：
- Q：infini-gram 查的是誰的資料庫，跟模型有什麼關係？
  A：查的是模型訓練時真正讀過的公開語料（Pythia 對應 Pile、OLMo-2 對應 Dolma/olmo-mix），這是選這兩個模型的唯一理由——訓練語料公開，才能拿它當「模型到底背過什麼」的鐵證，不用靠猜。
- Q：0/20 全滅那次，你們怎麼知道是程式錯了而不是這些名著真的沒被背過？
  A：連《傲慢與偏見》《創世記》這種公認被引用到爛掉的文本都查無，這種全部一起歸零的結果本身就不合常理；打開原始探針數據一看，果然是跨句窗口的標點被錯誤剝除，句子內部窗口計數其實都很健康。
