# 02. Token 與 Tokenizer（詞元與分詞器）

**一句話白話版**：模型不是照著「字母」或「中文字」讀文字的，它先把整段文字切成一塊一塊叫做 token（詞元，模型處理文字時的最小基本單位）的碎片，每個碎片對應一個數字編號，模型看到、算的、猜的全都是這些編號，不是我們肉眼看到的字。負責切碎片的工具叫 tokenizer（分詞器）。同一句話，Pythia 和 OLMo-2 這兩個模型用的切法常常不一樣——這件事在我們的研究裡不是小事，一個切法上的差異可以讓同一道題目在兩個模型上量到完全不可比的東西。

**為什麼本研究用得到**：本研究要跨兩個模型（Pythia-1.4B、OLMo-2-1B）比對「回憶 vs 創造」的訊號夠不夠一致才算數（製作歷程第十三步：「兩個不同血統的模型出現同樣的模式，訊號的可信度會上一個台階」）。但我們的核心量測之一（L1 事實回想，卡 09 的 gold logprob）常常是看「模型對正確答案這一個 token 的信心有多高」——如果同一個答案在兩個模型裡被切成的 token 數目不一樣、切法不一樣，這個「信心」數字在兩邊根本不是同一件事，跨模型比較就會失真。所以 tokenizer 的差異必須先被抓出來，當成共變量（covariate，統計上要拿來檢查、控制，而不是放著不管的干擾因素）處理，不然結論會被切法的雜訊污染。

**再深一點**：tokenizer 是一個事先訓練好的「切字字典」，它不是照單字切，而是照「哪些字元片段在訓練語料裡最常一起出現」切——常見的整個詞（像 `"the"`、`"Zeus"`）常常自己就是一個 token，少見或複雜的詞會被切成好幾個 token 片段（例如字首、字根各一塊）。Pythia 和 OLMo-2 分別在不同語料上訓練了各自的 tokenizer，所以「同一個字」在兩邊的切法可能完全不同：一邊是一整塊、另一邊是好幾小塊。這件事平常感覺不到，但在我們的實驗設計裡是要命的——因為很多量測是「模型對下一個 token 的機率」，如果答案在某個模型上被切成的第一塊是像 `" P"` 這種上千個詞都共用的碎片，那量到的「模型對這個答案的信心」其實只是「模型覺得下一個字母大概是 P 開頭的機率」，幾乎測不到跟「有沒有記得這個答案」有關的訊號。

**在我們的程式碼／數據裡**：`harness/build_battery_v2.py` 第 142–151 行，組完整份題庫（battery）後的最後一步，是替每一題都用兩個模型各自的 tokenizer 各算一次「這個提示詞、這個正確答案要幾個 token」（`prompt_tokens`、`gold_tokens` 兩個欄位），存進每一題的資料裡，當成隨數據一起攜帶的共變量。這個機制在 QC（品質查核）階段就抓到了兩個真實的坑，都記在 `battery/qc_report.json`：
1. **數字被 OLMo 拆成「空格＋數字」**：`GLOBAL-numeric-answer-tokenization` 項（severity: high）記錄，OLMo-2 會把 `" 56"`（前面帶空格的數字）切成 `" "` 加 `"56"` 兩塊，Pythia 卻是完整一塊。結果是：cloze 提示（卡 05 會細講這個格式）後面緊接著的第一個 token，在 OLMo-2 這邊只是一個空白符號，完全不帶答案資訊——`L1-cooking-1`（gold `100`，OLMo 2 token／Pythia 1 token）與 `L1-chess-1`（gold `64`，OLMo 2 token／Pythia 1 token）都中招。
2. **專有名詞被 Pythia 拆成好幾塊**：`GLOBAL-propernoun-tokenization-asymmetry` 項（severity: high）記錄，`" Poseidon"`（波賽頓）在 Pythia 被切成 `" P"` + `"ose"` + `"id"` + `"on"` 四塊，第一塊 `" P"` 是幾千個詞共用的碎片，幾乎不帶任何「這題在問希臘海神」的資訊；同一個詞在 OLMo-2 只切成 `" Pose"` + `"idon"` 兩塊。這一題最後被寫進正式題庫 `battery/battery.json` 對應項目（id `L1-Greek_mythology-2`）的 `qc_problem` 欄位，並要求分析時改用「整段答案的平均對數機率」而不是「只看第一個 token」來衡量記憶強度。

**常見誤解**：
1. 「tokenizer 只是技術細節，不影響研究結論」——在別的用途上或許如此，但在我們這種要「量測模型對某個特定答案的信心」的研究裡，tokenizer 的切法直接決定量到的數字有沒有意義。這也是為什麼 QC 報告特別把它列為 `severity: high`（高風險）的全域問題。
2. 「兩個模型的 tokenizer 應該差不多，畢竟都是英文」——不對，Pythia 和 OLMo-2 分別在不同語料（Pile 和 Dolma/olmo-mix）上訓練了各自的 tokenizer，常見詞的切法可能完全不同，愈冷門或愈專業的詞（人名、數字、術語）差異愈大。

**答辯模擬題**：
- Q：tokenizer 不一樣，那你們怎麼還能跨模型比較？
  A：兩個方法並用：一是把每題的 token 數存成共變量，分析時用它檢查、控制切法差異造成的干擾；二是像 gold logprob 這種關鍵指標改成量「整段正確答案」的平均信心，而不是只看第一個 token，這樣切法碎不碎，量到的東西都還是「模型信不信這整段話」。
- Q：你舉的 Poseidon 例子，是猜的還是真的測出來的？
  A：是真的用兩個模型各自的 tokenizer 實際編碼跑出來的結果，記錄在 `battery/qc_report.json` 和最終題庫 `battery/battery.json` 對應題目的欄位裡，不是猜測——這正是為什麼我們要在燒 GPU 之前先做這種「機械查核」，把猜測換成量出來的事實。
